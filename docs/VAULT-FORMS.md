# vault 形态选型:anc 是元库,不是一套固定架构

版本 0.1(2026-07-29)。

## 前提:anc 的产出是「这家公司该用哪套」

同一套 vault 规范(目录约定、frontmatter、`_originals/` 溯源、canonical 纪律、skill 名片)可以
跑在完全不同的基础设施上。**anc 是元库:`anc init` 的第一件事不是部署 Worker,而是判断这家
公司该用哪种形态。** 上来就给所有人同一套,要么是杀鸡用牛刀,要么是根本扛不住。

## 一刀切开:有没有 PDF

判据只有一条,因为它决定一切:**原件层的体量与最大单文件**。

结构化 markdown 那一层在任何公司都是 MB 级——几百 KB 到几 MB,怎么放都行。真正分开两个
世界的是扫描件、合同 PDF、影像、账套这些**原件**。

| | 形态 A:无(或少量)原件 | 形态 B:大量原件 |
|---|---|---|
| 典型构成 | 上百个 md + 几十个 PDF,原件层几十 MB | 几十个 md + 上千个原件,原件层 GB 级 |
| 最大单文件 | 几 MB | 几百 MB |
| **承载** | **git 仓库(GitHub private)** | **对象存储分层 + 本地镜像** |
| 基础设施 | 零 | 一个 Worker + 一个桶 |
| 成员怎么拿 | `git clone` / `git pull` | `anc pull` |
| agent 怎么读 | 直接 rg 工作区 | 直接 rg 本地镜像 |
| 原件怎么看 | 就在工作区里 | `anc open <路径>` 单取 |

**两种形态下 agent 的体验是一样的**:面对一个本地目录,`rg` / `Read`。区别只在这个目录是
怎么来的、原件在不在里面。这是刻意的——skill 与 vault 规范在两边完全通用,换形态不用重写任何约定。

## 判据的硬阈值(公开限制,可直接拿来判)

**git 路线的天花板**([GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)):

- 单文件 **> 100 MB 直接拒绝推送**(硬上限,不是警告)
- 仓库推荐 **< 1 GB**,强烈建议 < 5 GB;超了 clone 会显著变慢
- Git LFS 可以扛大文件(单文件上限 5 GB),但有存储/带宽配额,且给不会 git 的成员又加一层概念

**对象存储路线的天花板**:

- Cloudflare 请求体上限 **100 MB**(Free/Pro)/ 200 MB(Business)——单次 PUT 传不了更大的,
  需要 multipart 分片
- R2 单对象上限 5 TB;10 GB 免费存储;**egress 免费**(按需取原件不产生流量费)
- Worker 响应体无强制上限,流式透传 GB 级文件内存恒定

### 决策规则

```
原件层总量 < 1 GB  且  最大单文件 < 100 MB
    → 形态 A:git。别部署任何服务。
原件层 > 1 GB  或  存在 >100 MB 的单文件
    → 形态 B:分层。
成员里有人不会用 git,或者要接 IM bot 给非技术同事用
    → 形态 B(即使体量够小)——git 的心智负担会卡住一线成员
数据不允许出境 / 不允许上公有云
    → 形态 C:单机托管(一台常开机器上的目录),不上云
```

> 第三条比前两条优先级高:体量是技术问题,git 心智负担是采纳问题。一线成员在 IM 里问一句
> 就能拿到答案,和让他先学会 `git pull --rebase`,是两个世界。

## 形态 B 的关键设计:MCP 是控制面,不是数据通道

这条是形态 B 成立的前提,写清楚免得走回头路。

**agent 物理搬不动二进制。** MCP 的工具参数是模型逐 token 生成的字符串,一个 4 MB 文件
≈ 550 万 base64 字符 ≈ 150 万 token 输出。agent 内联上限实测约 **100–150 KB**。所以
「让 agent 通过 MCP 读写整个 vault」在体量上就是死的,跟 Worker 写得好不好无关。

四条接口按访问模式分开:

```
POST /mcp          控制面:list / read / search / write / history / original
GET  /manifest     index 层清单 {path, etag, size}——只 list 不读内容,带整体 ETag 支持 304
GET  /raw/<path>   流式透传(Range / If-None-Match),Worker 内存恒定
PUT  /raw/<path>   流式写入,原件默认只允许新建
```

分层规则贴合真实目录形态(`_originals/` 是嵌套在各项目里的,不是顶层前缀):

| 层 | 判定 | 同步 |
|---|---|---|
| index | 文本文件,且路径中无 `_originals` 段 | 全量镜像到本地 |
| originals | 路径中任一层目录名为 `_originals` | 不同步,按需单取 |
| history | `_history/` 开头 | 不同步,只读 |
| blob | 其余二进制 | 不同步,按需取 |

`<项目>/_ocr/` 下的 OCR 产物是 `.md`,自动落进 index 层——**穿透 grep 靠的是原件的文本投影,
不是原件本身**。扫描件没有文字层时 grep 在任何形态下都是零命中,那是 ingest 工序问题。

## 同源模型:Mac mini 不是特殊角色

托管形态(常开机器上的 IM bot)与 BYO 形态(每个人自己的 Claude Code)怎么读同一份真相源?

**答案是把它变成定义问题,而不是同步问题:真相源只有一份(git 远端 / 对象存储),
所有人——包括 Mac mini 上的 bot——都是它的客户端,地位完全相同。**

实测(形态 B,两个独立客户端):

- 两端各自 `anc pull` → 工作区逐字节一致
- 一端写入 → 另一端 `pull` 立刻拿到
- **bot 端只存 index 层(MB 级),原件缓存为空**;要看原件时按需取一份

反过来说:如果让 Mac mini 存全量原件,就有了两份,同源立刻破掉。**bot 不需要全量原件**——
它在 IM 里回答问题靠的是 md,要看原件时给链接或按需取。

形态 A 下同源更简单:两边都是 `git pull`,Mac mini 就是多一个 clone。

## 成本:不是「几百 GB 上云很恐怖」,是「大部分不该上」

先把账算清楚,免得凭直觉否掉一个其实很便宜的方案。R2 [公开定价](https://developers.cloudflare.com/workers/platform/pricing/):

| | 标准存储 | 低频访问存储 |
|---|---|---|
| 存储 | $0.015 / GB·月(前 10 GB 免费) | $0.01 / GB·月 |
| Class A(写 / list) | $4.50 / 百万(前 100 万免费) | $9.00 / 百万 |
| Class B(读) | $0.36 / 百万(前 1000 万免费) | $0.90 / 百万 |
| **出网流量** | **免费** | **免费** |

含 Workers Paid($5/月)的实际月账单:

| 总量 | 每月 |
|---|---|
| 100 GB | $6.4 |
| 300 GB | $9.4 |
| 500 GB | $12.4 |
| 1 TB | $19.9 |

**出网免费是这套设计的前提。** 「原件按需单取」意味着大量下载动作;换成按流量计费的对象存储
(多数国内云外网流出约 ¥0.5/GB),同样的用法会变成一笔随使用量波动的不可预测开销。R2 的成本
只跟存储量线性相关,与用得多不多无关。

### 但真正该做的是冷热分级

体积大头往往是在线价值最低的那部分:

| 类别 | 体积占比(典型) | 在线价值 |
|---|---|---|
| 结构化 md | 千分之几以下 | 最高,全员天天用 |
| 中小原件(<10 MB:合同、报表、审签表) | 约三成 | 高,复核要逐份调阅 |
| 影像、现场照片 | 大头 | 低 —— 上了也 grep 不到,是图不是文本 |
| 压缩包、账套、大备案资料 | 大头 | 极低,没人在线拆 zip |

所以分三档,而不是「全上」或「不上」:

- **热层**:md + `_ocr/` 文本 + <10 MB 原件 → 标准存储,随时调
- **冷层**:影像 / 压缩包 / 超大文件 → 低频访问存储,或不上云
- **不上云**:只在 vault 里登记一行「有此件、在何处」,由 `source_file` 指认

按这个分,实际上云量通常能降到全量的三成左右。**`anc init` 应当在部署前就估算出这个数字并
报价** —— 客户不该等到账单出来才知道花多少钱、哪些东西根本不必上传。

## 形态 B 的已知缺口与边界

诚实列清楚,选型时要一起交代给客户。

1. **>100 MB 的单文件目前传不上去。** 需要实现 R2 multipart 分片上传。在那之前,这类文件
   要么留在本地/所内存储只在 vault 里登记一行「有此件、在何处」,要么这家公司就不适合形态 B。
   **如果选择只登记,必须明说:此时「云上唯一一份」是不完整的。**
2. **权限。** 单 token 一家公司,谁有谁能读写全库。需要按项目/密级隔离时,
   **权限边界 = 部署边界**:同一份源码多部署一次,另一个桶、另一个 token。
3. **备份。** 对象存储里是唯一一份,`_history` 是版本历史不是备份。备份上线前,
   vault 不能是任何档案的唯一副本。
4. **合规。** 数据落在境外基础设施时,涉个人信息 / 政府国企底稿 / 有法定保存年限的档案,
   这是**先于技术的决策**。不可接受就换境内对象存储重新部署同一份逻辑,或直接走形态 C。
5. **manifest 性能。** 对象存储无法按扩展名过滤,`/manifest` 需全量 list 后在服务端筛。
   1000 量级的键是毫秒级;到 10 万量级需把清单物化并在写入时增量更新。当前有上限闸,
   触顶会显式标 `truncated`,不会假装完整。

## 形态 A 的边界

不是"小就没问题":

1. **成员必须会 git**,或者至少能容忍 `git pull` 这个动作。这条卡住的是采纳,不是技术。
2. **没有服务端强制。** 覆盖写靠 git 的合并机制,没有 read-before-write 护栏,
   也没有服务端注入的使用纪律(诚实条款只能写在 CLAUDE.md 里靠 agent 自觉)。
3. **仓库会随原件增长而变慢**,而 git 历史里的二进制删不掉。原件进 git 之前想清楚。
4. **接 IM bot 时**,bot 那台机器要有 clone 与拉取权限,凭据管理是额外一件事。

## 两种形态共享的东西

换形态不影响这些——这是 anc 作为元库的价值所在:

- 目录规范与路由 `CLAUDE.md`
- `_originals/` 只读溯源约定、`source_file` 互指
- frontmatter 与 canonical 单点维护纪律
- skill 名片机制(正文住 vault,改一次全员生效)
- 诚实条款(查不到就说「尚未入库」)
- OCR 产物落 `_ocr/` 成为可 grep 的文本投影
