# 跨公司技能分发安全设计

本阶段交付设计。运行中的公司 registry 只读取该组织的私有 vault。采用外部技能的前提是接收方明确给出分发需求、可信发布方与本地审核人。

## 发布身份与固定版本

发布方生成只包含一个技能的不可变包，清单记录组织与技能名、版本、每个相对路径、大小、执行位和 SHA-256 摘要。组织发布密钥对规范编码的完整清单签名。可采用 Ed25519，签名输入须含协议版本和用途标识。接收方通过独立渠道确认组织根密钥，限定发布键的名称空间、有效期及轮换权限。设计参照 [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)。

接收方锁定来源、签名键、精确版本和清单摘要，逐文件验签、验哈希；标签、分支与 latest 均不能充当版本锁。根密钥轮换、撤销列表、元数据有效期和单调版本计数用于拒绝过期与回滚。已批准的旧版本需要回退时，另存审核原因和目标摘要。可复用的元数据机制见 [TUF 规范](https://theupdateframework.github.io/specification/latest/)。

## 隔离扫描与审批

1. 在隔离区按清单核对包内全部对象和大小上限，拒绝绝对路径、目录越界、重复路径、链接和特殊文件。读取和扫描阶段不运行包内内容。
2. 静态检查 SKILL.md、引用文档、脚本与依赖清单。检查项覆盖诱导忽略权限或发送秘密的指令、未声明的网络或文件操作、凭据、不可检查的二进制和动态下载依赖。扫描失败或扫描器不可用时，包留在隔离区。
3. 安装前展示相对于接收方已批准版本的逐文件 diff。首次安装展示全量。突出可执行位、新工具权限、外发目标、依赖和删除项。评审记录绑定到同一个清单摘要；任何字节改变都需重审。
4. 在无业务数据和无外发能力的环境运行接收方维护的行为用例。审核人确认来源、扫描结果、权限和测试证据后，通过私有 vault 的 PR 引入精确版本。生产从该内部合并提交部署。
5. 审计记录保留签名与扫描器版本、锁定摘要、diff、审核人、评测结果及部署修订。发现撤销或异常后暂停该版本的新增部署，定位已安装组织，恢复最近获准的版本并复测。

验收样例应覆盖合法签名与锁定版本、内容被改写、已撤销的发布键、同名版本替换、隐藏的可执行文件、提示注入命中、扫描器失效，以及审核后替换包。静态检查通过仍需检查业务行为与所授权限。
